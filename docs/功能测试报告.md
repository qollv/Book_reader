### 3.2 最小化准备步骤

```bash
# 1) 安装依赖（含两个测试专用 dev 依赖）
cd /d/book_tool/novel_reader
flutter pub get

# 2) 运行测试（注意：必须清除代理变量）
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY \
    -u all_proxy -u ALL_PROXY flutter test
```

**两个环境注意事项（实测结论，非猜测）：**

1. **代理变量**：沙箱/部分环境设置了 `HTTP_PROXY` 等变量，Dart 的 WebSocket 连接会被代理劫持，导致 `flutter test` 整体挂起（表现为用例"did not complete"）。清除代理变量后恢复。
2. **flutter_test 的 MockHttpClient**：`TestWidgetsFlutterBinding` 会全局安装一个所有请求一律返回 400 的 Mock HttpClient（防止测试发真实网络请求的设计）。URL 导入等需要真实本地 HTTP 的测试，在基座 `test/functional/test_support.dart` 中通过 `HttpOverrides.global = null` 恢复真实客户端。新增 HTTP 相关测试时需保留该处理。
3. **FakeAsync 模型**：`testWidgets` 的 body 运行在 FakeAsync 作用域内，真实异步 I/O（sqflite / 文件）在 body 内直接 `await` **永远不会完成**，必须经 `tester.runAsync` 在真实异步区执行；页面自身 post-frame 回调（书架 load / 阅读器 repaginate / 设置持久化）也要在测试结束前排空，否则 tearDown 关闭数据库后回调才落地，会触发「使用已 dispose 的控制器」/「写已关闭的数据库」的 post-test 异常。基座中的 `drainRealAsync()` 即为此设计。

## 5. 缺陷列表

> 严重程度定义：P1 致命（主流程不可用）/ P2 严重（用户可见的功能错误）/ P3 一般（特定场景错误或不一致）/ P4 建议（健壮性/体验优化）。

### DEF-01（P2）md 导入的书名残留 `# ` 前缀

- **现象**：导入 md 文件后，书名取首行原样，`# 测试书2-山海食肆` 显示为「# 测试书2-山海食肆」（含 `# `）。
- **复现步骤**：导入 `test_books/测试书2-山海食肆.md`（首行为 `# 测试书2-山海食肆`）→ 查 `book.title`。锁定用例：FT-IMPORT-02。
- **代码位置**：`lib/core/parsers/book_parser.dart:26` `guessTitle()` 直接返回首个非空行；`markdown_parser.dart:95` 的注释表明正文侧已知 `# 标题`行并做了剥离，但书名侧未剥离 markdown 标题语法。
- **影响范围**：所有 md 导入用户；书架封面/书名、阅读器章节目录均显示异常书名。
- **修复建议**：`guessTitle` 对 md 输入先剥离行首 `#{1,6}\s+`（或由 MarkdownParser 传书名时剥离）。

### DEF-02（P3）纯 ASCII 二进制文件被当作正文导入

- **现象**：文件字节全部 < 0x80（纯 ASCII）但内容为二进制/控制字符时，编码防护不触发，文件被当正文导入，生成乱码书籍。
- **复现步骤**：构造仅含 ASCII 控制字符的文件 → 导入 → 得到一本书（应为拒绝）。锁定用例：FT-IMPORT-07。
- **代码位置**：导入管线的编码防护仅覆盖「非 ASCII 且解码失败」分支（FT-IMPORT-06 场景）。
- **影响范围**：误导入错误文件（如把可执行文件/日志当选书源）；书架出现乱码条目。
- **修复建议**：增加控制字符/可打印字符比例校验，超过阈值即拒绝。

### DEF-03（P3）书签合并完全忽略对端修改

- **现象**：本地已存在同 id 书签时，对端版本被无条件跳过，无冲突解决、无提示。对比笔记有 `updated_at` last-write-wins，书签没有。
- **复现步骤**：本地插入 id=bm-shared 书签（comment 为空）→ 对端推同 id 不同 comment 的书签 → 合并后本地 comment 仍为空。锁定用例：FT-SYNC-04。
- **代码位置**：`lib/services/sync/sync_service.dart:100-106`；根因是 `Bookmark` 模型无 `updated_at` 字段（只有 `created_at`）。
- **影响范围**：多设备用户的书签内容无法同步更新（如对端补了批注）。
- **修复建议**：`Bookmark` 增加 `updated_at`，合并逻辑与笔记对齐（last-write-wins）。

### DEF-04（P4）对端返回非对象 JSON 时 download 抛 TypeError

- **现象**：同步对端返回 JSON 数组（如 `[1,2,3]`）时，`download` 抛 TypeError 而非可读错误。
- **复现步骤**：HTTP 服务返回 `[1,2,3]` → 调 `download`。锁定用例：FT-SYNC-08。
- **代码位置**：传输层的 `jsonDecode(...) as Map<String, Object?>` 强转（`lib/services/sync/sync_transports.dart`）。
- **影响范围**：需对端返回畸形数据才触发；书架同步入口有 try/catch 兜底为「同步失败」提示，无数据损坏。
- **修复建议**：`jsonDecode` 结果先 `is Map` 判断，非对象时抛 ImportException 或返回 null。

### DEF-05（P3）device_id 非 String 时 fromJson 抛 TypeError

- **现象**：对端 payload 的 `device_id` 为数字等非 String 时，`SyncPayload.fromJson` 抛 TypeError。设计注释声称「逐条过滤掉结构不符的条目而非整体崩溃」，但顶层字段没有安全转型。
- **复现步骤**：`SyncPayload.fromJson({'device_id': 12345})`。锁定用例：FT-SYNC-06a。
- **代码位置**：`lib/services/sync/sync_service.dart:34` `json['device_id'] as String?`。
- **影响范围**：对端为旧版本/第三方实现时同步整体失败。
- **修复建议**：`json['device_id'] is String ? ... : 'unknown-device'`。

### DEF-06（P3）首同步不上传本地数据，同步无法自举

- **现象**：`download` 返回 null（对端无数据，首次配对/空端点）时，`sync` 直接返回空报告，**不上传**本地数据。
- **复现步骤**：本地已导入书 → FakeTransport(download=null) → sync → 断言 `transport.uploaded`（当前为 null）。锁定用例：FT-SYNC-07a。
- **代码位置**：`lib/services/sync/sync_service.dart:80-83`。
- **影响范围**：两台新设备首次配对时互相等对方先推数据，同步永远无法启动；新设备加入既有环境也拿不到数据。
- **修复建议**：`remote == null` 时也应构造本地 payload 上传（空对端 + 本地有数据 = 首次播种）。

### DEF-07（P3）打开阅读失败时 `_book` 未清空

- **现象**：`openBook` 在已赋值 `_book` 之后、加载章节/正文期间抛异常时，catch 只设置 `_error`，`_book` 残留当前书引用。
- **复现步骤**：导入书 → 破坏其 `contentPath` 正文文件 → 重新 openBook → 断言 `controller.book`（当前非 null）。锁定用例：FT-RC-02。
- **代码位置**：`lib/state/reader_controller.dart` `openBook()` 的 catch 分支。
- **影响范围**：无可见 UI 影响（ReaderScreen 渲染优先级 error > page，用户看到错误页）；属内部状态不一致，后续依赖 `_book` 的代码路径有隐患。
- **修复建议**：catch 分支补 `_book = null; _chapters = []; _pages = [...]`。

### DEF-08（P3）`as num?` 不防类型错误（既有修复不完整）

- **现象**：对端书签 `chapter_index` 等字段为字符串时，`as num?` 仍抛 TypeError——`as T?` 只防 null，不防类型错误。
- **复现步骤**：`SyncPayload.fromJson({'device_id': 'd', 'bookmarks': [{'id': 'x', 'chapter_index': 'not-a-number'}]})`。锁定用例：FT-SYNC-06b。
- **代码位置**：`lib/services/sync/sync_service.dart` 书签/笔记解析段。
- **影响范围**：同 DEF-05——对端数据字段类型不符时同步整体失败。
- **修复建议**：统一改为 `is` 判断 + 默认值（如 `(json['chapter_index'] as num?)` → `json['chapter_index'] is num ? ... : 0`）。

### DEF-09（P3）设置项通知被持久化阻塞，UI 反馈延迟

- **现象**：`SettingsController.update()` 先 `await _settingsDao.save()` 再 `notifyListeners()`——持久化完成前 UI 不刷新。真实环境持久化慢时设置面板点击后外观延迟生效；快速连续点击 SegmentedButton 时，第二次落在「视觉旧选中态」上的点击会被按钮吞掉（测试环境复现，见 FT-UI-05 注释）。
- **复现步骤**：在 FakeAsync 测试环境连续切换显示模式（FT-UI-05 首次运行即暴露）；真实环境可用慢速存储复现延迟。
- **代码位置**：`lib/state/settings_controller.dart:22-26`。
- **影响范围**：设置交互体验；快节奏操作下点击丢失。
- **修复建议**：先 `notifyListeners()` 再 await 持久化（或持久化转后台任务），失败时回滚状态并提示。

### P4 观察项（非缺陷，需产品确认）

- **显式「日间」+「夜间」配色不强制深色**：`theme_mode_resolver.dart` 注释称「夜间配色强制走深色主题」，但实现为显式模式优先——用户显式选日间又选夜间配色时，`resolveThemeMode` 返回日间。当前测试按实际行为断言（FT-UI-05）。若与设计意图不符，需修正实现或注释。

## 6. 测试结论与改进建议

### 6.1 总体结论

1. **可发布性判断**：核心业务流程（导入 → 阅读 → 进度/书签/笔记 → 设置 → 同步 → 删书）功能正确，96/96 用例通过、静态分析 0 issues。**未发现阻塞主流程的缺陷**，按当前质量可以进入发布前打磨阶段。
2. **质量亮点**：容错设计整体到位——打开失败有错误页、导入异常有中文友好文案、同步畸形数据有逐条过滤、设置脏数据回落默认值、越界操作被安全忽略。
3. **主要风险点**：① md 书名显示异常（DEF-01，用户可见，建议优先修）；② 多设备同步的书签不同步与首同步无法自举（DEF-03/06，影响同步功能可用性）；③ 对端数据防御性解析不完整（DEF-05/08，影响互联互通）。

### 6.2 修复优先级建议

| 优先级 | 缺陷 | 理由 |
| --- | --- | --- |
| 1 | DEF-01 | 唯一用户直接可见的功能错误，改动极小（ guessTitle 剥离 `# `） |
| 2 | DEF-06 + DEF-03 | 同步功能可用性：首同步自举 + 书签 last-write-wins |
| 3 | DEF-05 + DEF-08 | 对端防御性解析，改为 `is` 判断即可，可同一次改动完成 |
| 4 | DEF-02 + DEF-07 + DEF-09 | 特定场景/内部一致性，排入常规迭代 |

- 本次新增 `test/functional/` 共 7 个测试文件 + 1 个共享基座 `test_support.dart`，与原有测试互不干扰，`flutter test` 一把全跑。
- 基座要点：内存 sqflite（schema 与 `AppDatabase._createTables` 手工镜像，**schema 演进时需同步 `test_support.dart` 的 `createSchemaForTest`**）、假 path_provider、`HttpOverrides.global = null`、`drainRealAsync()`。
